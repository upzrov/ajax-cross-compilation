# Аналіз результатів (Завдання 6)

## Загальний огляд
В ході виконання роботи було створено інформаційний С-застосунок, який виводить системні дані (hostname, час, ОС, апаратну платформу) та вміє записувати їх у файл. Процес розробки та тестування включав кілька етапів: нативну компіляцію на HOST, крос-компіляцію для TARGET системи (як динамічну, так і статичну) та нативну компіляцію безпосередньо на TARGET. 

## 1. Проблеми та особливості крос-компіляції (Крос-розробка)
Крос-компіляція (компіляція на HOST для виконання на TARGET) супроводжується низкою типових проблем та особливостей:
- **Різні архітектури процесорів**: HOST зазвичай x86_64, тоді як TARGET - часто ARM (наприклад, aarch64, armhf). Через це скомпільований на HOST звичайним `gcc` бінарний файл завершиться помилкою `Exec format error`, якщо спробувати запустити його на TARGET. 
- **Toolchain (Набір інструментів)**: Для крос-компіляції потрібен специфічний набір інструментів (наприклад, `arm-linux-gnueabihf-gcc`). Усі утиліти (`readelf`, `ldd`, `size`, `strings`) також мають бути версіями з toolchain (наприклад, `arm-linux-gnueabihf-readelf`), оскільки HOST утиліти можуть не розпізнати або некоректно інтерпретувати ELF файл іншої архітектури.
- **Відмінності у бібліотеках (libc)**: Цільова система може мати іншу версію стандартної бібліотеки С (glibc, musl, uClibc). Якщо застосунок скомпільовано динамічно, на HOST використовується версія бібліотеки крос-компілятора, але при запуску на TARGET програма шукатиме бібліотеку, встановлену на TARGET. Якщо версії або архітектури не збігаються, програма не запуститься (помилка `cannot open shared object file` або `version GLIBC_... not found`).

## 2. Перенесення та виконання програми
- При перенесенні (через `scp`, `rsync`, чи USB) може втратитись біт виконання (executable bit). Перед запуском на TARGET необхідно зробити файл виконуваним: `chmod +x sysinfo_target`.
- У динамічно слінованій програмі на TARGET має бути наявний відповідний інтерпретатор ELF (`ld-linux.so...`), який вказаний в `.interp` секції бінарника.

## 3. Порівняльний аналіз: Динамічна vs Статична лінковка
При порівнянні результатів крос-компіляції (`3_build_cross.sh`) та статичної лінковки (`5_build_cross_static.sh` з прапорцем `-static`):
- **Залежності (`ldd` / `readelf -d`)**: 
  - Динамічна версія має секцію `NEEDED` та залежить від спільних об'єктів (зазвичай `libc.so.6`).
  - Статична версія покаже повідомлення "not a dynamic executable" або не матиме секції `DYNAMIC`, оскільки всі необхідні функції бібліотек вже вбудовані у сам файл.
- **Розмір файлу (`size`)**: 
  - Динамічна програма є відносно невеликою, оскільки не включає в себе код стандартних бібліотек.
  - Розмір статично скомпільованого файлу є **значно більшим** (часто у сотні разів), оскільки він включає код всієї `libc`, необхідний для роботи програми, незалежно від наявності бібліотек на цільовій системі.
- **Гнучкість та безпека**: Статичний бінарник легше переносити між різними версіями однієї TARGET платформи (він запуститься завжди, навіть якщо на TARGET бракує бібліотек). Однак він споживає більше пам'яті та дискового простору, а також не отримує автоматичних оновлень безпеки (якщо в `libc` знаходять вразливість, програму доведеться перекомпілювати).

## 4. Нативна компіляція на TARGET (Завдання 4)
- Нативна компіляція уникає проблем із розбіжністю архітектур і відсутністю бібліотек, але **забирає більше часу та ресурсів**. TARGET системи (Raspberry Pi, мікрокомп'ютери) часто мають обмежені ресурси процесора та пам'яті. 
- Розгортання повного середовища розробки (gcc, binutils, headers) займає багато місця на накопичувачі TARGET системи, що часто є небажаним або неможливим для embedded пристроїв. Тому крос-компіляція на потужному HOST ПК є галузевим стандартом, незважаючи на додаткові складнощі налаштування toolchain.
